# Known issues and gaps

A running log of anything that turned out to be weird, inconsistent, undocumented, or missing while building this map. Three kinds of entry live here:

- **Ethereum itself** — spec inconsistencies, unspecified behaviour, client disagreement, things that arguably need fixing upstream.
- **This map** — terms a lesson had to explain in prose because no node exists for them, and facts we could not pin down.
- **This repo** — bugs found, and work still owed.

## How to add to it

Add an entry the moment something is noticed, not later. One entry, one problem. Keep this shape:

```
- **Short label** — what is wrong or missing, and why it matters. Status: open | resolved | upstream | by design.
```

Say what is actually known. If a claim is unverified, write that in the entry rather than dropping it. When an entry is resolved, move it to **Resolved** with a one-line note on what fixed it, rather than deleting it.

Proposed map nodes are written as slugs in backticks, for example `precompiles`. A test asserts none of those slugs already exists as a topic, so once a term gets its own node the test fails until the entry moves to **Resolved**. That is deliberate: it stops this file drifting out of date quietly.

## Ethereum protocol and spec

- **No standard code for "execution reverted" on `eth_call`** — Geth, Nethermind and Reth commonly return JSON-RPC error code `3` with the revert bytes in `data`, while several hosted providers return `-32000` with a message string. The execution-apis error-group catalogue (#650, March 2026) now defines code `3` "Execution reverted", alongside gas errors in 800–999 and txpool errors in 1000–1199, but only `eth_sendTransaction` and `eth_sendRawTransaction` reference it, so a read that reverts is still unspecified. Callers cannot branch on code alone and end up matching on message text. Status: open, upstream (partly addressed).
- **`pending` is not specified** — the tag names a block that does not exist yet, assembled from one node's own transaction pool. Some clients and most hosted endpoints quietly answer `latest` instead. Any read against `pending` is therefore node-specific and not reproducible. Status: open, upstream.
- **`eth_estimateGas` has no agreed default block tag** — clients differ on whether an omitted block parameter means `latest` or `pending`, which changes the answer whenever a pending transaction touches the same state. Pass the tag explicitly. Status: open, upstream.
- **Two ways to ask for the chain** — `eth_chainId` (EIP-155) and `net_version` both exist, return different encodings, and can disagree on forked or misconfigured networks. `net_version` is effectively legacy but still widely called. Status: open, upstream.
- **QUANTITY and DATA are easy to confuse** — quantities are minimal hex with no leading zeros (`0x0`), byte strings are fixed-width and keep their zeros. The execution-apis schemas do encode the rule as patterns (`uint` is `^0x(0|[1-9a-f][0-9a-f]*)$`, hashes and addresses are exact-length) and the spec's test vectors are checked against them; what is missing is enforcement in clients, where whether a node rejects a malformed value, or emits one, is up to its own parser. Mixing the two silently corrupts balances, storage keys and signatures. Status: open, upstream.
- **`eth_getLogs` has no standard limits or pagination** — the method takes a block range with no defined maximum, so every provider invents its own caps (block span, result count, wall-clock timeout) and its own error text. Portable log scanners have to discover limits by failing. Status: open, upstream.
- **Tracing is only partly standardised** — `debug_` descends from Geth and `trace_` from Parity, and they model the same execution differently. Since June 2026 (#762) execution-apis specifies `debug_traceTransaction`, `debug_traceBlockByNumber` and `debug_traceBlockByHash` with a standardised opcode tracer, but `trace_` is still absent and call-frame semantics (which frames appear, what `value` a frame carries) still differ between clients and tracers. Anything built on call traces is written against one client family. Status: open, upstream (opcode traces addressed).
- **No agreed definition of an "internal transaction"** — tools choose which trace frames count. Erigon's and Reth's `ots_getInternalOperations` count every non-zero-value CALL, every CREATE and CREATE2 (even with zero endowment) and SELFDESTRUCT, skip the top-level frame, and keep frames that an enclosing revert undid, while Geth's and Parity-style tracers disagree even on whether precompile calls are frames. Explorers and deposit scanners built on different clients can therefore disagree about the same transaction. Status: open, upstream.
- **No standard method returns a transaction or receipt proof** — `eth_getProof` (EIP-1186) covers account and storage state only. Nethermind's `proof_getTransactionByHash` and `proof_getTransactionReceipt` return Merkle-Patricia inclusion proofs against `transactionsRoot` and `receiptsRoot`, optionally with the RLP header, and `Proof` is in 2.0's default module list, but no spec defines them. Everywhere else, proving that a transaction or a log was included means rebuilding the trie from a full block, which every bridge and light client reimplements. Status: open, upstream.
- **Historical `eth_getProof` availability is undefined** — an archive node holds historical state, but generating a proof also needs the historical trie nodes, which some storage layouts discard. "Archive" is therefore not a reliable promise of provable history, and Succinct's RSP documentation reports providers whose proofs for older blocks are simply invalid, which shows up only as a state-root mismatch after the prover has done its work. Status: open, upstream.
- **Filters are server-side session state** — `eth_newFilter` and `eth_getFilterChanges` bind a client to one node, which breaks behind any load balancer that does not pin sessions, and they expire on an unspecified idle timeout (Geth's default is five minutes). Status: open, upstream.
- **`eth_syncing` returning `false` does not mean usable** — a node can report not-syncing while still lagging the head, or while its consensus client is down and its `finalized` view is frozen. Health checks that trust it alone are wrong. Status: open, upstream.
- **`mixHash` carries `prevRandao`** — after the Merge the header field kept its pre-merge name in most RPC responses, so the JSON field name no longer matches what the value means. execution-apis itself uses both: its block schema has `mixHash` as a 32-byte hash, while `eth_simulateV1`'s block overrides call the same value `prevRandao` and type it as a `uint256`, so a caller that reads a block and then overrides one handles the same 32 bytes under two names and two encodings. Status: open, upstream.
- **`safe` has two meanings, and a caller cannot tell which** — the consensus specs used to define the safe block as the block at the latest justified checkpoint, about 6 to 13 minutes behind the head; since consensus-specs #4747 (merged 2026-04-16, with #5278) `safe_block_hash` must come from the Fast Confirmation Rule, which confirms blocks much closer to the head. Most consensus clients ship the rule switched off: Lighthouse (v8.3.0) and Prysm (v7.2.0) behind `--enable-fast-confirmation`, Lodestar behind `--chain.fastConfirmation`, Teku behind the hidden `--Xfast-confirmation-enabled`, and Grandine only in an open pull request (#656), while Nimbus feeds it into the safe hash by default since v26.6.0. Two endpoints can therefore answer `safe` minutes apart, and nothing in the Engine API or JSON-RPC says which rule produced it. Status: open, upstream.
- **`contractAddress` does not mean a contract exists** — the receipt field is filled in for every contract-creation transaction, including one that reverted and deployed nothing. Tools that treat a non-null `contractAddress` as a successful deployment are wrong; the status field and `eth_getCode` are what tell you. Status: open, by design.
- **"Has code" no longer means "is a contract"** — since EIP-7702 a key-controlled account can carry code, the 23-byte delegation designator, so on-chain guards and off-chain tools that classify accounts by the presence of code misread delegated accounts, and `tx.origin == msg.sender` no longer rules out contract code running. Status: open, by design.
- **Signature checkers send EIP-7702 delegated EOAs to ERC-1271** — OpenZeppelin's `SignatureChecker` (v5.7) and USDC's FiatToken v2.2 use `ecrecover` only when the signer has no code, so a plain ECDSA signature made by a delegated EOA's own key goes to `isValidSignature` on the account, which runs the delegate's code, and is rejected if the delegate does not implement ERC-1271 or expects rehashed input. That includes USDC `permit` and `transferWithAuthorization` from delegated accounts, and ERC-6492's reference validator never reaches `ecrecover` for such an account either. viem's `verifyHash` falls back to `ecrecover`, while the x402 reference facilitator deliberately does not, because the fallback "causes pre-verify to accept sigs the on-chain token rejects (empirically confirmed on Base Sepolia)", a code comment that is the first empirical confirmation found. Status: open, upstream.
- **An address with no code behaves differently depending on who calls it** — an `eth_call` sent straight to it succeeds and returns `0x`, while a Solidity contract calling a function on it reverts with empty data. The same empty `0x` therefore means success on one path and failure on the other: a payment simulated against a token address that holds no code passes and then settles as a silent no-op, which is why the x402 reference facilitator rejects an `asset` with no code. Status: open, by design.
- **`ecrecover` and `P256VERIFY` report failure as empty success** — invalid input returns no output rather than failing the call, while most other precompiles consume all forwarded gas on bad input. Solidity's `ecrecover` turns the empty output into `address(0)`, which is the root of the classic unset-owner signature bug. Status: by design.
- **An MEV-Boost proposer signs a block it has not seen** — on the builder path the proposer signs a blinded block that carries only the payload header, and the relay publishes the payload afterwards. The proposer is trusting the relay both that the payload is valid and that it will be published; if either fails, the slot is lost. Status: open, by design, with enshrined proposer-builder separation as the upstream direction.
- **The relay's block-validation method has no specification** — `flashbots_validateBuilderSubmissionV*` is defined by no EIP and no execution-apis schema, and mev-boost-relay picks the version by fork (V3 Deneb, V4 Electra, V5 Fulu) under a configurable namespace. Reth serves V3 to V6, Nethermind only V3, upstream Geth nothing, and the Flashbots Geth fork that defined it is archived. A relay operator learns compatibility by trying it. Status: open, upstream.
- **builder-specs' bid verification signs the wrong object** — `verify_bid_signature` computes the signing root over `signed_registration.message` inside a function whose argument is `signed_bid`; it should be `signed_bid.message`. Cosmetic, but it is the reference text for bid verification. Status: open, upstream.
- **builder-specs and the market disagree on the fee recipient** — the honest-validator spec's `process_bid` asserts that the header's fee recipient is the proposer's registered address, yet most MEV-Boost blocks name the builder and pay the proposer with a final transfer. Relays accept either after simulation (Reth's validation explicitly allows both) and MEV-Boost does not apply the spec's check, so an implementation that follows the spec as written rejects most real bids. Status: open, by design in practice.
- **Links into consensus-specs have broken twice** — its default branch is now `master`, so every `blob/dev/...` URL returns 404, and builder-specs still links that way throughout; separately, consensus-specs #5523 (August 2026) moved SSZ to ethereum/ssz-specs, breaking links into its `ssz/` directory. Specs that cite each other by URL rot silently. Status: upstream.
- **No standard interface for preconfirmations** — no `eth_` method requests or returns one, and commitments are not recorded in blocks. Base Flashblocks (through `pending`), Taiko's preconfers and Commit-Boost modules each expose their own surface, and Bolt, the reference L1 implementation, is archived. Wallets and simulators cannot ask portably what has already been promised ahead of them. Status: open.
- **No API reports a proposer's execution-layer income** — the Beacon API reward routes and the `Eth-Consensus-Block-Value` header cover consensus rewards only. Execution income has to be reconstructed from the block, as the fee recipient's balance change or the builder's closing transfer, or taken from relays' own reports, so every staking dashboard reimplements it. Status: open.
- **Refusing a typed-data signature for the wrong chain is only a recommendation** — EIP-712 says a wallet should refuse to sign when the domain's chainId differs from the active chain, but it is a should, not a must, and wallet behaviour varies. A dapp cannot rely on the wallet to catch a cross-chain replay for it. Status: open, upstream.
- **A blob transaction's hash is not the hash of what you sent** — `eth_sendRawTransaction` for a type-3 transaction takes the network form, which carries the blobs, commitments and proofs, but the transaction hash is computed over the transaction without that sidecar. Hashing the submitted bytes yourself gives a hash no node will recognise. Status: open, by design.
- **Rejecting a below-base-fee transaction is client-dependent** — some clients queue it until the base fee falls, others refuse it outright. A submitter sees either a hash that never lands or an immediate error, for the same transaction. Status: open, upstream.
- **Layer 2 reuses `eth_` names with different meanings** — `safe` and `finalized` on an OP Stack chain are derived from L1, block times are seconds or milliseconds rather than twelve, and receipts carry extra L1 fee fields. Code written against L1 semantics compiles and runs against an L2 while being subtly wrong. Status: open, upstream.
- **History expiry still makes a by-hash "not found" ambiguous** — execution-apis #636 (October 2025) added error `4444` "Pruned history unavailable" to the block, receipt and log methods, and Geth, Reth and Nethermind (#12090) return it for block-addressed queries below their cutoff. A lookup by transaction hash goes through the transaction index first, though, and once the index no longer covers the hash Geth returns `null`, the same answer as "never mined": `4444` cannot fire when the node does not know which block to name. Whether Geth and Reth error or silently shorten an `eth_getLogs` range that straddles the boundary was not checked. Status: open, upstream (block-addressed case addressed by #636).
- **Running out of retained state has no error code** — a query below a node's state window fails with free text (`missing trie node`, `historical state not available`, a pruned-history message) that differs per client, and Nethermind 2.0's release notes record that it even answers "no state for that block" with different codes depending on the method (#13603). Providers add their own: one public endpoint refused a historical `eth_call` with `-32602` "Archive requests require a personal token…", the invalid-params code. A caller cannot tell "outside the window" from any other failure without matching strings. Status: open, upstream.
- **Retention is advertised now, but not by every endpoint you meet** — execution-apis specified `eth_capabilities` in June 2026 (#755, merged 2026-06-02), reporting the head and, per resource, the oldest block and the delete strategy, and Geth v1.17.4, Nethermind 1.39.0, Reth v2.3.0, Erigon v3.5.0 and Besu 26.5.0 serve it. Older releases and many gateways do not, and a gateway may refuse it with `-32600` "Unsupported method" rather than `-32601` (seen on 2026-10-29 behind a `reth/v2.5.2` version string), so a router that treats only `-32601` as "not supported" misclassifies it and still has to probe for boundaries by failing. Status: upstream, implemented; deployment partial.
- **History file formats are churning** — the e2store specs now mark era1 deprecated in favour of ere and add E2HS (headers with Portal proofs), E2SS (flat state snapshots) and Erb (blobs). Nethermind calls ere "EraE" and still accepts the older `.erae` extension, and Geth and Nethermind write only the `noproofs` profile, so their post-Merge exports are not self-verifying. EIP-7643, whose accumulator root pre-Merge files anchor on, is Stagnant. Status: open, upstream.
- **JSON-RPC has no cancellation** — neither JSON-RPC 2.0 nor the execution-apis spec defines a way to cancel a request in flight, and whether a node stops executing an `eth_call` or a trace when the caller disconnects is client-specific and undocumented. Quote engines and solvers that abandon stale simulations keep paying for work nobody will read. Status: open, upstream.
- **The pool only announces arrivals** — `newPendingTransactions` reports a transaction entering one node's pool, but no standard event reports it being replaced, evicted or dropped. A submitter learns a transaction is gone only by polling and inferring from the account nonce. Status: open, upstream.
- **Bundle methods are builder conventions** — `eth_sendBundle` and `eth_callBundle` came from Flashbots and are served mainly by block builders; Reth is an exception among execution clients, answering `eth_callBundle` from its standard `eth` module and `mev_simBundle` behind `mev`. No EIP defines them, and builders extend the parameter set differently, so bundle code is written against one builder's dialect. Status: open, upstream.
- **`eth_callBundle`'s `gasPrice` has two meanings** — in the Flashbots docs' example a transaction's `gasPrice` is `coinbaseDiff / gasUsed` (476,190,476,193 wei for a transaction that tipped 3 wei), while Reth reports the effective priority fee per gas. The same field carries different values depending on who answers. Status: open, upstream.
- **Bundle methods abandon QUANTITY encoding** — `eth_callBundle` returns wei amounts as decimal strings and `gasUsed`, `totalGasUsed` and `stateBlockNumber` as JSON numbers while taking `blockNumber` as hex, and `eth_sendBundle` takes `minTimestamp` and `maxTimestamp` as JSON numbers, yet alloy serialises `eth_callBundle`'s `timestamp` as a hex quantity. Parsers written for `eth_` conventions misread them. Status: open, upstream.
- **Flashbots errors are not JSON-RPC-shaped** — the Flashbots RPC docs say their methods follow JSON-RPC for success responses but not for errors (V2 methods excepted), so a client's normal envelope handling cannot parse them. Status: open, upstream.
- **Flashbots describes its signature recipe two ways** — the prose says `X-Flashbots-Signature` signs "the EIP-191 hash of the json body", while all three code samples personal-sign the hex string of `keccak256(body)`. The code is what works, and the prose misleads implementers. Status: open, upstream (docs).
- **Cancelling a bundle is best effort** — `eth_cancelBundle` keeps a bundle out of future builder bids but does not withdraw bids already at a relay, so a cancelled bundle can still land. The docs also disagree on where it works: the cancellations page says `relay-staging.flashbots.net` only, while the endpoint page documents it on `relay.flashbots.net`. Status: by design (best effort); open (docs).
- **Enhanced provider APIs are not portable** — token balance, NFT and transfer-history endpoints are each provider-specific, so the convenient path off the standard surface is also the one that locks a project in. Status: open, by design.
- **The `eth_` prefix does not say who answers** — ERC-4337 bundler methods are named `eth_sendUserOperation` and `eth_getUserOperationReceipt`, but no execution client implements them; they are served by a bundler. Wallet methods under `eth_` are answered by the wallet. The namespace tells you nothing about which process handles the call. Status: open, upstream.
- **ERC-4337 is Final, but the rules that make it safe are not** — ERC-4337 puts the validation rules and the bundler RPC out of scope; they live in ERC-7562 (Review) and ERC-7769 (Draft). The public mempool's safety therefore rests on documents that can still change. Status: open, upstream.
- **ERC-7769 contradicts itself** — its `eth_sendUserOperation` parameter list says `paymasterValidationGasLimit` where the struct in the same document, and ERC-4337, say `paymasterVerificationGasLimit`. Its example "paymaster stake too low" response uses `-32504`, which the text assigns to throttled or banned entities (stake too low is `-32505`), and `-32506` is missing from the list, so bundlers that copy the example return the wrong code. Status: open, upstream.
- **Two error code spaces** — EIP-1193 defines provider errors `4001`, `4100`, `4200`, `4900` and `4901` alongside the JSON-RPC `-32xxx` range. A browser dapp has to handle both, and the two overlap in meaning without mapping onto each other. Status: open, upstream.
- **EIP-3085 forbids the RPC URLs local devnets use** — it says a wallet MUST reject `http:` and `file:` RPC URLs in `wallet_addEthereumChain`, which strictly excludes `http://127.0.0.1:8545`, yet wallets accept such URLs in practice. The EIP is also marked Stagnant despite universal use, and its abstract misspells the method as `wallet_addEtherereumChain`. Status: open, upstream.
- **The chain registry ships dead and API-keyed RPC URLs** — on 2026-09-28 ethereum-lists/chains listed `https://rpc.sepolia.org` (HTTP 404) and `https://rpc2.sepolia.org` (no connection) first for Sepolia, plus an Alchemy URL with an embedded API key. Chainlist and wallets that seed from the registry inherit them. Status: open, upstream.
- **EIP-6963's `uuid` lifetime is underspecified** — the EIP says `uuid` distinguishes provider sessions "during the lifetime of the page" and `rdns` is the stable identifier, but it does not say whether a wallet must regenerate the uuid on each load, and its own reference wallet hardcodes one. A dapp cannot tell a repeated uuid meaning the same session from a wallet that never changes it. Status: open, upstream.
- **`personal_sign` and `eth_sign` take their arguments in opposite orders** — one is `[message, address]`, the other `[address, hash]`, for two methods that are otherwise easy to confuse. The argument order is the only thing stopping a caller signing the wrong thing. Status: open, upstream.
- **CCIP-Read signals success by reverting** — EIP-3668 offchain lookup is triggered by a specific revert, so a plain `eth_call` cannot resolve an offchain ENS name and instead sees a failure. Resolution requires a client that recognises the revert and follows it, and an endpoint that passes the revert data through: a provider that answers reverts with `-32000` and no `data` makes every offchain name unresolvable, with no error that says why. Status: open, upstream.
- **CCIP-Read has no notion of a block** — the gateway request carries only `sender` and `callData`, so an offchain answer is always "now" and a historical resolution cannot be reproduced. ethers v6 follows a lookup only when the call's block tag is `latest`, so a pinned-block call surfaces the raw revert, while viem appears to run its callback `eth_call` at the default block even when the original call was pinned (read from source, not tested). The same pinned query can fail in one library and silently mix blocks in the other. Status: open, upstream.
- **CCIP-Read makes a server fetch URLs a contract author chose** — a backend that resolves ENS names with a library that follows lookups issues HTTP requests to whatever URL template the resolver returns. EIP-3668 allows URLs of any scheme and discusses browser fingerprinting, but says nothing about server-side request forgery toward internal hosts. Status: open, by design.
- **Multicall3 swallows `OffchainLookup`** — `aggregate3` never bubbles a sub-call's revert: with `allowFailure` the lookup comes back as `(false, returnData)`, and without it Multicall3 reverts with its own error. An offchain name batched through Multicall3 cannot be resolved the way EIP-3668 describes, so libraries that auto-batch reads have to special-case it. Status: open, by design.
- **ERC-20 and ERC-721 share a `Transfer` topic0** — the signature hash is identical, and only the number of indexed topics distinguishes a fungible transfer from an NFT transfer. Log consumers that filter on topic0 alone mix the two. Status: open, upstream.
- **ERC-3009's text and its main deployment disagree** — the ERC defines only `v, r, s` functions and now says it does not apply to smart-contract accounts, while USDC's FiatToken v2.2 adds `bytes signature` overloads (`0xcf092995`, `0x88b7ab63`, `0xb7b72899`) checked through ERC-1271. Decoders and indexers keyed on the ERC's selectors miss those calls, and the ERC is still a Draft after years of production use in USDC and now x402. Status: open, upstream.
- **Blob commitments outlive blob data** — the KZG commitment stays in the chain forever while the blob itself is dropped from the consensus layer after roughly eighteen days, so a commitment can be verifiable long after the data it commits to is unavailable from nodes. Status: open, by design.
- **Expired blobs cannot be backfilled from the network** — Fulu deprecates the by-range and by-root blob sidecar requests, and peers need serve data columns only for 4,096 epochs, about eighteen days. A blob archive therefore has to be running before the data expires, or copy another archive. Status: by design.
- **The Beacon API blob route moved** — beacon-APIs v4.0.0 (October 2025, for Fulu) added `GET /eth/v1/beacon/blobs/{block_id}` with a `versioned_hashes` filter and deprecated `/eth/v1/beacon/blob_sidecars/{block_id}` (#546), and the v5.0.0 alphas remove both it and the `blob_sidecar` event (#577). The new route's description says only supernodes are required to return blobs after Fulu, and current op-node releases call only the new route. Tools and guides written against `blob_sidecars` break once clients drop it. Status: upstream.
- **Orphaned logs are only announced on one path** — a subscription and `eth_getFilterChanges` both set `removed: true` when a reorg withdraws a log, but `eth_getLogs` simply stops returning it. A consumer that polls has no in-protocol way to learn that a log it already stored is gone, which silently corrupts naive indexers. Status: open, upstream.
- **Block-by-timestamp helpers disagree on convention** — there is no standard method. Erigon's `erigon_getBlockByTimestamp` returns the first block at or after T, and returns the head for a future T and genesis for a T before it rather than an error, while Etherscan's `getblocknobytime` makes the caller choose `closest=before|after`. Governance snapshots and airdrop cut-offs get different blocks depending on the helper, and Snapshot's `multichain` strategy maps a vote's block to other chains through one off-chain service, `blockfinder.snapshot.org`, whose before-or-after rule is undocumented and which caches by the hour. Status: open, upstream.
- **`eth_getProof` is welded to one state tree** — EIP-1186 describes its result purely in Merkle-Patricia terms, as arrays of RLP trie nodes, with no version marker and no abstraction over the tree type. Any future state-tree change breaks the method's schema rather than just its contents. Status: open, upstream.
- **The same value has two names in one response** — the account leaf field is `storageRoot` while the `eth_getProof` response field is `storageHash`. Status: open, upstream.
- **`eth_getProof` disagrees on absent accounts** — for an address with no leaf, Geth (since v1.13.4, go-ethereum #28357), Nethermind and Erigon return zero hashes for `codeHash` and `storageHash`, while Besu and Reth (by default) return the empty-code hash `0xc5d2…a470` and the empty-trie root `0x56e8…b421`, exactly what an existing empty account returns; hosted providers split the same way. EIP-1186 never defines the case, although a Nethermind source comment says it does. Callers that detect existence from these fields, or cache responses across clients, get different answers for the same block. Status: open, upstream.
- **EIP-1186's absence rule leaves out extension nodes** — its "Proofs for non existent values" describes a proof ending at a branch with an empty slot or at a leaf with a different path, and says nothing about a key diverging inside an extension node's segment, which is equally valid and occurs on mainnet. Verifiers written from the EIP alone reject valid proofs. Status: open, upstream.
- **`requireCanonical` is an unverifiable assertion** — EIP-1898's flag is the only canonicality control in the whole JSON-RPC surface, and it is the answering node's word for it. Nothing in the response lets the caller check. Status: open, upstream.
- **A trie cannot say "never written" versus "written back to zero"** — both produce an exclusion proof, so contracts have to carry a separate flag to recover the distinction the protocol discards. Verkle would have kept it (EIP-6800 commits a present zero differently from an empty position, and EIP-4762 says 0 is distinct from None), and the EIP-7864 binary tree also hashes an empty leaf differently from a stored zero, so whether a binary tree recovers the distinction depends on keeping EIP-4762's access-event rules. Status: open, upstream.
- **ethereum.org's verkle page is stale** — it still presents verkle as the path in progress, and does not mention EIP-6800 going Stagnant, the March 2026 removal of its consensus specs (consensus-specs #4984), or the move to the EIP-7864 binary tree. Readers and vendors keep citing it as the roadmap. Status: open, upstream.
- **Hard-coded generalized indices break at forks, and will again at Glamsterdam** — Electra grew the beacon state from 28 to 37 fields, moving `FINALIZED_ROOT_GINDEX` from 105 to 169 and the sync committee indices from 54 and 55 to 86 and 87, and Deneb moved the payload's `block_hash` within the body from 412 to 812; a non-upgradeable beacon-root verifier breaks for good. EIP-7688 (scheduled for Glamsterdam) ends that churn with progressive containers, but its own activation renumbers everything once more (the finalized root becomes 735), so every verifier needs another release timed to Gloas. Status: open, by design (fix scheduled).
- **Gloas light client headers drop the execution state root** — under EIP-7732 the payload leaves the beacon block body, and the Gloas `LightClientHeader` carries only an `execution_block_hash`, proven from the bid's `parent_block_hash`. A verified-RPC stack that reads `execution.state_root` from the header must instead fetch an execution header from an untrusted node, check its hash and take `stateRoot` from it, and the proven hash is the parent payload's, so it trails the beacon block. Glamsterdam has been live on Sepolia since 2026-10-06; Hoodi's activation was withdrawn and mainnet is unscheduled. Status: upstream.
- **Light clients may advance without a supermajority** — the two-thirds threshold applies only to advancing the finalized header and rotating the committee: validation accepts an update with a single participant, the optimistic header moves on more than half of recent peak participation, and after a sync committee period without finality `process_light_client_store_force_update` MAY apply the best update seen "based on use case dependent heuristics", promoting an attested header to finalized. What a light client guarantees during long non-finality therefore depends on an implementation heuristic. Status: by design.
- **Anonymous events cannot be filtered by signature** — they have no `topic0`, so no `eth_getLogs` filter can select them by name. The filter semantics say nothing about the case. Status: open, upstream.
- **A block can name blob data nobody has** — after the roughly eighteen day sidecar retention, `eth_getBlockByNumber` still returns the blob transaction, and no error distinguishes "this data expired" from any other kind of missing data. Status: open, upstream.
- **EIP-5792 atomicity depends on the account, not the call** — `wallet_sendCalls` does not guarantee that a batch is atomic; that depends on what kind of account is behind it. It also returns an identifier that is not a transaction hash, so the usual receipt polling does not apply. Status: open, upstream.
- **Withdrawal and consolidation requests can fail silently** — the EIP-7002 and EIP-7251 contracts check only the fee and the input length, and the consensus layer then drops a request without effect when the source address does not match the withdrawal credentials, the validator is inactive, already exiting or too new, a partial withdrawal targets a non-compounding validator, or the partial-withdrawal queue is full. The transaction still succeeds, the fee is kept (overpayment is never refunded), and nothing on the execution side reports the outcome. Status: by design.
- **Execution requests are not exposed over JSON-RPC** — the block object carries `requestsHash` but no requests list, and withdrawal and consolidation requests come from the return data of end-of-block system calls, which have no receipt; the authoritative list is only in the beacon block's `execution_requests`. A request can also be dequeued in a later block than the one that submitted it, so the contract's log on submission does not say when the consensus layer received it. Status: open, upstream.
- **System calls change state without a transaction** — the start-of-block writes of beacon roots (EIP-4788) and block hashes (EIP-2935), and the end-of-block calls to the EIP-7002 and EIP-7251 contracts, change storage with no transaction, receipt or per-transaction trace. A storage-diff indexer sees changes it cannot attribute: Geth's block tracer runs the start-of-block calls untraced and never runs the end-of-block ones, and Erigon, Nethermind and Reth were not checked. Glamsterdam's block-level access lists (EIP-7928) do record these writes, at index 0 before the transactions and n+1 after them. Status: by design.
- **No RPC field reports the gas a transaction needed** — receipts report post-refund `gasUsed`, which can be well below the limit the transaction required, because refunds are applied after execution and EIP-150 withholds a 64th at each call. The only standard pre-refund figure is `maxUsedGas` in `eth_simulateV1` results, added to the schema in March 2026 (#746); which clients fill it was not checked. Status: open, upstream.
- **`movePrecompileToAddress` is described two ways in one schema** — in `eth_simulateV1`'s state-override schema the `state` variant says moving a non-precompile is undefined and clients may differ, while the `stateDiff` variant says only precompiles can be moved. Status: open, upstream.
- **The Beacon API event stream cannot resume** — the eventstream spec defines no `id:` field, so `Last-Event-ID` has nothing to resume from and every reconnect loses the gap; consumers have to backfill over REST. Status: open, upstream.
- **An endpoint cannot describe its own surface** — OpenRPC defines `rpc.discover` for a server to return its own document, but execution clients serve `rpc_modules` instead, which maps namespaces to `"1.0"` and says nothing about methods, parameters or limits; a code search of Geth, Nethermind, Besu, Reth and Erigon found no `rpc.discover`. The spec is machine-readable, but a given endpoint's subset of it is not. Status: open, upstream.
- **Ephemery's spec and tooling drift apart** — the spec says the reset period must be "high enough so network cannot be overtaken" while its own table implies it must be short enough, and it derives a unique fork digest by overwriting `validators[0].withdrawal_credentials` while the genesis builder instead adds a dummy validator carrying the iteration number. The README's Pectra note also cites "iteration 3943814", which looks like a truncated chain id. Status: open, upstream.
- **Gnosis Chain changes withdrawal and fee semantics** — the `withdrawals` array is processed by a system call to the deposit contract's `executeSystemWithdrawals` rather than by crediting balances (the GNO is then claimed with `claimWithdrawal`), bridged xDAI is minted by a post-block system call to the reward contract, and the base fee goes to a fee collector instead of being burned. Generic tools that apply mainnet semantics miscount all three. Status: by design.
- **Gnosis applied an irregular state transition** — the December 2025 Balancer recovery fork (timestamp `1766419900`) set the code of EOA `0x506d1f9efe24f0d47853adca907eb8d89ae03207` through client configuration, with no transaction (`rewriteBytecodeTimestamp` in Nethermind's chainspec). Replay and code-history tools have to special-case it. Status: by design.
- **Glamsterdam changes what the transaction gas cap caps** — EIP-7825 (Fusaka) limits any transaction's gas limit to 16,777,216. Glamsterdam's EIP-8037, as specified at the time of writing, lets the limit go up to 2^32−1 and applies the cap to execution gas only, so wallet, pool and tooling code that rejects any limit above 2^24 breaks where Glamsterdam is active: on Sepolia since 2026-10-06, not on Hoodi, whose activation was withdrawn, and not yet scheduled for mainnet. Status: upstream.
- **The execution-apis documentation site lags the spec** — the published pages have no entries for `debug_trace*` or `debug_getRawBlockAccessList` although the spec now defines them, while `txpool_` and `eth_capabilities` do have pages; and `web3_`, which every client serves, is not in the spec at all. Readers of the site see a smaller standard than the one that exists. Status: open, upstream.
- **`eth_call`'s default sender is unspecified, and contracts depend on it** — execution-apis does not say which `from` a call without one uses; Geth and Nethermind (in source) and Reth (on a live node) use the zero address. Balancer v3's `VaultExtension.quote` and `quoteAndRevert` revert with `NotStaticCall()` unless `tx.origin` is zero, and Chainlink Automation's `cannotExecute` accepts only the zero address or `0x1111…1111`, so a caller that fills `from` in, as wallets and viem with an `account` do, breaks them. Status: open, upstream.
- **`eth_simulateV1`'s default block time: the spec says one second, clients use a slot** — execution-apis `BlockOverrides.time` says an unset time "is incremented by one for each block", while Geth (`timestampIncrement = 12`), Nethermind (`SecondsPerSlot`) and Reth (the chain's block time, falling back to 12) all add 12 seconds on mainnet, so a test written to the spec text fails on all three. And because `eth_call` at `latest` runs with that block's own number and timestamp while `eth_simulateV1` builds a child block on top of it, the same call can branch differently in the two methods. Status: open, upstream.
- **`traceTransfers` adds nothing where EIP-7708 is active** — execution-apis now says no synthetic `0xeeee…eeee` logs are added in blocks where EIP-7708 makes every ether transfer emit a real `Transfer` log from `0xffff…fffe`, and Geth skips its synthetic tracer there. A consumer that filters for `0xeeee…eeee` sees no ether movements on Sepolia, which has run Amsterdam since 2026-10-06, and will see none on mainnet after the fork. Status: by design.
- **JSON-RPC failures arrive as HTTP 200** — a reverted call or a `missing trie node` error comes back in a 200 response, and execution-apis defines no mapping to HTTP status, so a load tool that does not parse bodies counts failures as fast successes; vegeta treats any 200 as success, which is why flood added `--deep-check`. Rate-limit errors such as `-32005` are the exception that providers commonly send with 429. Status: by design.
- **Reads have no privacy, and verification leaks more** — every state read names its subject in cleartext parameters, and a Helios-style verifying client adds an `eth_createAccessList` and an `eth_getProof` per touched account, so the provider learns more about each call than before. TEE-based RPC and private information retrieval are roadmap items (Buterin, April 2025), not deployed defaults. Status: open (research).
- **EIP-7773 lists a Hoodi Glamsterdam activation that did not happen** — the meta EIP's table still gives Hoodi epoch 132352 (2026-10-26), but eth-clients/hoodi #33 removed `amsterdamTime` and the Gloas epoch on 2026-10-22, giving no reason, and on 2026-10-29 Hoodi blocks carried no `blockAccessListHash` or `slotNumber` and Geth's `eth_config` there showed no next fork. Glamsterdam is live only on Sepolia (epoch 353024, 2026-10-06 13:53:36 UTC), with no mainnet date, so anyone scheduling from the EIP's table expects behaviour Hoodi does not have. Status: open, upstream.
- **EIP-7732 is in Last Call while a public testnet runs it** — its Last Call ends 2026-11-01 and `specs/gloas/beacon-chain.md` still calls itself work in progress, yet Sepolia activated Gloas on 2026-10-06. The current design differs from 2025 descriptions: builders are a separate registry funded by EIP-8282 deposit requests, a payload's state effects are applied in the next block, and a withheld payload's bid is still paid at the end of the following epoch if 60% of one slot's stake attested to the block, so material written from older sources is likely stale. Status: open.
- **Under the Fast Confirmation Rule, `safe` can move backwards** — when the rule's checks fail (the confirmed block is from before the previous epoch, off the canonical chain, or fails the epoch-start recheck) it falls back to the finalized checkpoint, so `safe` can drop by dozens of blocks in one forkchoice update, and after a restart it starts from finalized unless the client implements the spec's optional restore step, as Lighthouse does. Consumers that assume `safe` only advances break. Status: by design.
- **Under Gloas, `safe` and `finalized` sit one payload further back** — `specs/gloas/fork-choice.md` takes `finalized_block_hash` from the finalized block's bid `parent_block_hash`, and the Gloas fast-confirmation spec says "only the parent payload of a confirmed beacon block is safe". Each tag therefore ends one execution block further from the head than the same checkpoint did before Gloas. Status: by design.
- **Under Gloas the execution chain can reorg under a canonical beacon block** — a payload already imported with `engine_newPayload` and `engine_forkchoiceUpdated` is dropped if the next proposer builds on its parent as EMPTY. Beacon API consumers may not see it: `head_v2` must fire again on empty-to-full, but emission on full-to-empty "is optional and implementation-defined", and the old `head` event is deprecated (beacon-APIs #590). Status: open.
- **Beacon events carry no execution block hash before Gloas** — `head`, `block` and `block_gossip` name only beacon roots, so mapping one to an execution hash means fetching `/eth/v2/beacon/blocks/{root}`, which serves only imported blocks. `payload_attributes` carries `parent_block_hash`, but the spec leaves its frequency to node configuration and Lighthouse emits it on every fork-choice update only with `--always-prepare-payload`; the Gloas pre-release adds `block_hash` to `block`. Status: by design (changes with Gloas).
- **The Beacon API cannot say why it returned no blobs** — after Fulu only supernodes are required to return blobs and other nodes "may implement blob reconstruction logic", so a caller cannot tell "this node does not custody enough columns" from "pruned" or "no such blobs". Lighthouse answers 400 `Insufficient data columns to reconstruct blobs: required 64, but only N were found…`; other clients' status codes and bodies differ and were not checked. Status: open, upstream.
- **EIP-3076 never left Last Call** — the slashing-protection interchange format's Last Call deadline was 2021-11-03, and in October 2026 it is still in Last Call although every consensus client, Web3Signer and the keymanager API implement it. Status: open, upstream.
- **System-contract failures are handled asymmetrically** — if the EIP-4788 or EIP-2935 contract has no code the system call fails silently and blocks stay valid, whereas missing code at the EIP-7002 or EIP-7251 request contract makes the block invalid. A chain or devnet that forgets to deploy a history contract keeps producing blocks, and every getter call just returns empty data. Status: by design.
- **`eth_capabilities` cannot describe partial retention** — the schema allows one `oldestBlock` per resource, forbids extra members (`additionalProperties: false`) and defines only the `window` delete strategy. A Nethermind node keeping history for chosen addresses (`FlatDb.HistorySliceAddresses`), a Reth node pruning receipts by log filter (`--prune.receiptslogfilter`), or a node still building an index has no way to say so. Status: open, upstream.
- **The `eth_capabilities` OpenRPC example is an impossible answer** — PR 819 replaced the test fixture because it paired head `0x13f8e3a` with the mainnet genesis hash and gave `receipts` a window Geth never emits, but `src/eth/capabilities.yaml` keeps that same example, so generated docs show it. Status: open, upstream.
- **EIP-7864 contradicts itself since its June 2026 revision** — the 2026-06-24 commit added a type byte and cut the header stem's share to 16 code chunks (`CODE_OFFSET` 4) and 4 slots (`HEADER_STORAGE_OFFSET` 20), but left an invariant `STEM_SUBTREE_WIDTH > CODE_OFFSET > HEADER_STORAGE_OFFSET` that is now false, prose that still says 64 slots and 128 chunks, an aligned-range note the storage function contradicts, a storage-key function using undefined `STORAGE_OFFSET` and `chunk_id`, and a `hash()` limited to 32- or 64-byte inputs that `stem || 0x00 || root` and the 33-byte code-chunk key input exceed. With no test vectors, an implementer cannot derive keys or stem hashes unambiguously. Status: open, upstream.
- **EIP-7864's hash choice has flip-flopped** — a 2025-02-27 commit was titled "Finalize hash function selection to Poseidon2", while the current text calls BLAKE3 a placeholder ("Do not assume BLAKE3 is a final decision") with Keccak and Poseidon2 as candidates. Anything that verifies proofs on chain needs the chosen hash in the EVM, which has an opcode for Keccak but no precompile for BLAKE3 or Poseidon2. Status: open, upstream.
- **The binary tree's fork and migration EIPs still describe verkle** — EIP-7864 delegates its fork to EIP-7612 ("Verkle state transition via an overlay tree", Stagnant, requiring EIP-6800) and its migration to EIP-7748 ("State conversion to Verkle Tree", Draft, `CONVERSION_STRIDE` TBD). Nothing specifies the overlay or the conversion for the binary tree itself. Status: open, upstream.
- **An account's nonce no longer counts the transactions it sent** — under EIP-7702 each applied authorization increments the authority's nonce even when a sponsor sends the transaction, and a delegated account's code can run `CREATE`, raising it mid-transaction. So `eth_getTransactionCount` matching the number of outgoing transactions is no completeness check for accounts that delegate; a contract's nonce, separately, counts its creations and starts at 1 (EIP-161). Status: by design.
- **ERC-20 lets a failed `transfer` return `false`** — EIP-20 says `transfer` SHOULD throw on insufficient balance and that callers MUST handle `false`, so a deposit pipeline that credits from decoded calldata plus a successful receipt `status` can be fooled by a token that returns `false`, the "false top-up" pattern SlowMist has warned about. Only the token's logs or balances show whether anything moved. Status: by design.
- **USDT on Ethereum changes balances without `Transfer` logs** — the 2017 TetherToken's `issue` and `redeem` emit only `Issue(uint)` and `Redeem(uint)`, `destroyBlackFunds` emits only `DestroyedBlackFunds`, `AddedBlackList(address)` has no indexed parameter to filter on, and `transfer` returns nothing, so a contract calling it through a `bool`-returning interface reverts. Supply and balances rebuilt from `Transfer` logs never match `totalSupply` or `balanceOf` for this token. Status: by design.
- **ERC-721 lets a contract assign tokens without an event** — EIP-721 allows any number of NFTs to be created and assigned during contract creation without emitting `Transfer`, and ERC-2309's `ConsecutiveTransfer` replaces `Transfer` for ranges ("the Transfer event MUST NOT be emitted"). An ownership table built only from `Transfer` logs is incomplete by specification. Status: by design.
- **ERC-5805 both requires and merely recommends ERC-6372** — its header lists EIP-6372 under Requires while the body says contracts SHOULD implement it and otherwise use a block-number clock, and `getPastVotes` for a future timepoint only SHOULD revert (OpenZeppelin 4.2–4.8 say `ERC20Votes: block not yet mined`, 4.9 `ERC20Votes: future lookup`). `getPastTotalSupply`, which quorum calculations use, is an OpenZeppelin addition rather than part of the ERC, and both ERCs are still in Review, so a generic reader cannot rely on the revert or on `CLOCK_MODE` existing. Status: open, upstream.
- **ERC-4626 `max*` returning 0 is ambiguous** — EIP-4626 says `maxDeposit` and `maxWithdraw` MUST return 0 when the action is disabled and lets all four `max*` functions underestimate, and Morpho Vault V2 returns 0 from all four by design while deposits are open. An integrator reading the standard interface cannot tell "disabled" from "not computed". Status: by design.
- **ERC-6492's reference validator repeats every failed ERC-1271 check** — for a signature without the suffix on an address with code, a failing `isValidSignature` triggers the retry with `tryPrepare = true`, which has no factory call to run and so calls the same function again, doubling the gas of every invalid contract signature. Solidity's `try`/`catch` also does not catch a failure to decode return data, so a contract whose fallback returns nothing makes the validator revert with empty data instead of returning `false`. Read from the reference code, not run. Status: open, upstream.
- **ERC-6492's `prepare` form runs calldata the signer chose** — the ERC says a verifier cannot tell a pre-deployment wrapper from a prepare call on a deployed account and must try both, and its security section assumes simulation only. A verifier that executes the wrapper as a real transaction, as the x402 facilitator does at settlement, runs signer-chosen calldata, which is why the x402 reference code requires an `eip6492AllowedFactories` allowlist, empty by default. Status: open, upstream.
- **The Chainalysis sanctions oracle is frozen but still answers** — Chainalysis's page says the oracle is "no longer supported or maintained", last updated 18 March 2026, yet `isSanctioned` at `0x40C57923924B5c5c5455c48D93317139ADDaC8fb` still answers on mainnet. A contract or service that screens through it gets an ageing list with no on-chain sign that it stopped changing. Status: open.
- **Chainlink SVR delivers one price two ways** — for Aave's SVR feeds the report reaches the SVR aggregator privately through MEV-Share and the standard aggregator through the public mempool, and Aave v3 on Ethereum prices WETH, LINK and AAVE from SVR proxies. A bot watching public `AnswerUpdated` logs or transmissions for "the price Aave uses" watches the wrong contract for those assets, and the SVR feed falls back to the standard price only after a configurable delay. Status: by design.
- **Flashbots' MEV-Share documentation contradicts itself** — the "Sending Bundles" page sends `mev_sendBundle` to `rpc.flashbots.net`, while the client library and the rate-limit page use `relay.flashbots.net`; and "Understanding Bundles" says a bundle holding `{hash}` entries may not use `privacy`, while the builder-inheritance note has searchers narrow builders through the bundle's `privacy.builders`. An implementer cannot tell which rule the node enforces. Status: open, upstream (docs).
- **A MEV-Share backrun cannot be simulated before it lands** — `mev_simBundle` rejects a bundle that still holds an unmatched `{hash}` entry, so a searcher prices a backrun from the hints alone. Status: by design.

## Client behaviour worth knowing

Recorded because a lesson needed it and the answer was not in one obvious place. Verify against the version you run before depending on any of it.

- **Geth and Nethermind prune the transaction index** — Geth's `--history.transactions` and Nethermind's `Receipt.TxLookupLimit` both default to about the last 2,350,000 blocks, so `eth_getTransactionByHash` and `eth_getTransactionReceipt` stop finding older transactions even though the block is still present. Nethermind keeps every entry with `0`; Reth keeps its index under `--full` and drops it under `--minimal`; Erigon and Besu were not checked. Reads as data loss if you do not know the setting exists. Status: by design.
- **Erigon serves RPC from a separate process** — `rpcdaemon` is its own component, so "the node is up" and "RPC is up" are separate facts.
- **`ots_` support is uneven, and `ots_getApiLevel` hides it** — Erigon implements the whole Otterscan namespace at API level 8, with its address searches on dedicated inverted indexes. Reth registers every `ots_` method and also reports level 8, but `ots_searchTransactionsBefore` and `ots_searchTransactionsAfter` return `-32603 unimplemented` (reth #13499), so Otterscan's address-history pages fail against it; Anvil implements all of them, but its searches cover only blocks Anvil mined itself, after the fork point in fork mode. A code search found no `ots_` in Geth, Nethermind or Besu, and because the API level does not describe coverage, gating on it does not detect support. Status: open.
- **Path-based state keeps a short window** — Geth's default scheme retains roughly the last 128 blocks of state, so historical `eth_call` fails on a node that looks fully synced.
- **"Full node" no longer means "all history"** — Nethermind 2.0 raised the mainnet `Sync.AncientBodiesBarrier` and `Sync.AncientReceiptsBarrier` defaults from 15,537,394 to 24,600,000, so a new or resynced default node holds no bodies or receipts from before about March 2026. Erigon v3.5's default `--prune.mode=full` keeps blocks and receipts for only 262,144 blocks (about 36 days, the EIP-8252 window), and v3.6 stopped persisting receipts by default; Reth `--full` drops pre-Merge bodies. Indexers that assume a full node has every block since genesis break silently. Status: by design.
- **A restored database is not re-verified** — none of the clients checked re-verifies a copied datadir on start: new blocks exercise only the accounts they touch plus stored intermediate hashes, and nothing checks change sets, the transaction index or the log index. Only an explicit pass (`geth snapshot verify-state`, Nethermind's `FlatDb.HistoryVerifyEveryBlock`) closes the gap, and snapshot checksums (Reth's BLAKE3 manifest, Nethermind's `Snapshot.Checksum`) come from the same source as the snapshot unless pinned in a shipped config. Status: by design.
- **Era1 imports anchor on the files' own source by default** — without `Era.TrustedAccumulatorFile`, Nethermind checks each file's checksum against the list in the same directory and verifies its content, but compares the resulting accumulator with nothing independent, so the imported history is only as trustworthy as whoever supplied the directory (read from the 2.0.0 source). Geth's `import-history` checks each file's SHA-256 against the `checksums.txt` in the same directory; whether it also checks accumulator roots against EIP-7643 was not traced, although `download-era` embeds mainnet and Sepolia checksums. Status: open.
- **Metrics ports are not standardised** — each client exposes Prometheus on its own port and flag. Nothing is shared across clients, so dashboards are per-client.
- **Beacon API default ports differ by client** — Lighthouse and Nimbus serve it on 5052, Teku on 5051, Lodestar on 9596, and Prysm's REST gateway on 3500. Health checks and tooling that assume one port silently miss three of the five consensus clients.
- **Light client data is optional, and off by default in some consensus clients** — Lighthouse serves it unless `--disable-light-client-server` is set, Prysm only with `--enable-light-client`, and Teku only behind a hidden `--Xrest-api-light-client-enabled`, default false; Nimbus, Lodestar and Grandine were not checked. A beacon endpoint chosen at random may answer 404 on `/eth/v1/beacon/light_client/*`, and full nodes are only asked (SHOULD) to keep bootstraps and updates for about five months. Status: by design.
- **Topics that are not 32 bytes are handled differently** — Geth rejects an `eth_getLogs` filter whose topic is not 32 bytes, for example an unpadded 20-byte address. Whether other clients reject it or quietly match nothing was not confirmed, so a filter that "works" against one client can return an empty result on another.
- **`eth_call`'s `gas` includes the intrinsic cost** — the call object's `gas` is treated like a transaction gas limit, so 21,000 plus the calldata cost is deducted before execution. On Geth v1.17.1, `gas: 0x5000` fails with `intrinsic gas too low: have 20480, want 21240`, so a caller emulating an on-chain sub-call budget such as ERC-165's 30,000 must add about 21,000. The execution-apis spec does not say so, and only Geth was tested. Status: by design.
- **A wrong Engine API secret and a skewed clock look the same from outside** — both surface to the consensus client as an unauthorised request, so the cause is only visible in the execution client's own log.
- **Validator rewards depend on the validating execution client's RPC load** — attestations are due at `ATTESTATION_DUE_BPS` 3333, about 4 seconds into the 12-second slot (2500 after Gloas), and importing the block includes `engine_newPayload` execution, so public RPC load on the execution client behind a validator directly costs head votes. Whether any client prioritises Engine API work over JSON-RPC was not checked. Status: by design.
- **Every consensus client names the execution endpoint differently** — Lighthouse and Prysm use `--execution-endpoint`, Teku `--ee-endpoint`, Nimbus `--el` (formerly `--web3-url`), Lodestar `--execution.urls`. A configuration translated flag by flag from one client to another breaks, and the older Nimbus name still appears in guides.
- **Grandine's flags could not be confirmed** — no flag names or default API port are asserted in its lesson, which is why it is the only client topic without an example. Status: open, needs someone who runs it.
- **`eth_simulateV1` support is uneven** — it arrived across the major execution clients during 2024 and 2025, so availability depends on the version in front of you rather than on the client name.
- **The two tracing families are not translations of each other** — `debug_` returns a call tree and takes a tracer argument, `trace_` returns a flat action list; the field names differ too, and Besu has neither in the same form. Tooling picks a family and stays there.
- **Tracers disagree on calls to precompiles** — Geth's `callTracer` records `CALL` and `STATICCALL` frames to precompiles, Geth's `flatCallTracer` drops them unless `includePrecompiles` is set (following Parity, whose traces omit them), and Reth's Parity-style `trace_` excludes them by default. Internal-call counts and explorer views built on different tracers differ for the same transaction. Status: open.
- **A DELEGATECALL frame's `value` depends on the tracer** — Geth's tracer docs say `value` appears only on real transfers, but its EVM hands a DELEGATECALL frame the parent's value ("DELEGATECALL inherits value from parent call") and `callTracer` reports it, while Reth's `ots_traceTransaction` reports `null`. Anything that sums `value` over Geth frames counts inherited value twice. Read from source. Status: open, upstream (the docs, or the field's meaning).
- **Transient storage is invisible to state-diff tracing** — Geth's `prestateTracer` and the struct logger's `storage` map track `SLOAD` and `SSTORE` only; transient values appear only as `TLOAD` and `TSTORE` stack operands in an opcode trace, and no Geth tracer has a transient-storage output. Status: open.
- **Geth's tracers outlive a cancelled request, and lose their timeout** — the goroutine that enforces a trace's `timeout` cancels the EVM only when that deadline passes, so if the request context ends first, through a client disconnect or Geth's own `-32002 request timed out` at the 30-second HTTP write timeout, the trace runs to completion and its own deadline never fires. Block tracing stops dispatching transactions but finishes the one in progress, whereas `eth_call` cancels the EVM on any context end. Read from source, v1.17.6 and master. Status: open.
- **`debug_executionWitness` has no specification and several shapes** — Geth, Reth, Erigon, Nethermind and Besu all have a method of that name in current source, but it is not in execution-apis. Geth returns `headers` as JSON objects and never fills `keys`, Reth, Erigon and Nethermind return RLP header bytes and fill `keys` (Nethermind's shape read from its types), Besu returns only `state`, `codes` and `headers`, and Reth's optional second parameter (`legacy`, the default, or `canonical`) changes the content. Provers such as Zeth depend on the method and document that many providers lack it. Status: open, upstream.
- **Bundlers need tracers that hosted RPC rarely allows** — ERC-7562 enforcement needs `debug_traceCall` with a JavaScript tracer (Rundler, Alto, the reference bundler) or Geth's native `erc7562Tracer` (v1.16.0+). Hardhat node and Ganache cannot run it, and hosted endpoints commonly disable `debug_` or allow only named tracers, which pushes bundler operators to `--unsafe` mode; which other execution clients run the JavaScript tracer was not checked. Status: by design.
- **graph-node's docs and code disagree on what `traces` means** — its configuration docs say the `traces` provider feature means `debug_traceBlockByNumber` support, but its Ethereum adapter fetches call triggers with `trace_filter`, which The Graph's own docs name as the requirement. An operator who marks a Geth endpoint as `traces` gets failing call handlers, since Geth has no `trace_` namespace. Status: open, upstream (docs).
- **Firehose needs patched client builds** — the Firehose tracer is not in upstream Geth, whose live tracers are only `supply` and `noop`, or in upstream Reth, so extended Firehose data depends on StreamingFast or others keeping forks in step with every client release. Status: by design.
- **Historical balance and historical proof are separate promises** — flat and path-based storage layouts let a node answer `eth_getBalance` at an old block while failing `eth_getProof` at that same block. Nothing in the spec relates archive state to archive trie nodes. Geth 1.17 (`--history.trienode`), Nethermind 2.0 (`FlatDb.ArchiveProofBuildEnabled` with `FlatDb.ArchiveProofServeEnabled`, #13098) and Erigon 3 (`--prune.include-commitment-history`) now offer historical proofs as opt-ins, off by default, and Reth serves them only within `--rpc.eth-proof-window`, which defaults to 0 and is capped at 1,209,600 blocks.
- **`eth_getBlockReceipts` support still varies** — enough that the lessons document the single-block `eth_getLogs` fallback rather than assuming the method is there.
- **Outside its log index, each client fails differently** — Geth quietly falls back to a block-by-block bloom scan, including when its indexer has disabled itself after hitting a missing receipt (v1.15.7), so a broken index shows only as slow queries. Nethermind without `LogIndex.Enabled`, which is off by default, rejects a wide range with `-32602` under `Receipt.MaxBlockDepth`, Reth has no log index and caps the blocks scanned per filter (`--rpc.max-blocks-per-filter`, default 100,000), and Erigon since v3.4.0 rejects ranges wider than 1,000 blocks (`--rpc.blockrange.limit`) and stops at 20,000 logs (`--rpc.logs.maxresults`). No method reports which blocks an index covers or whether it is still being built. Status: open, upstream.
- **Geth's log index covers about a year, even on an archive node** — `--history.logs` defaults to 2,350,000 blocks independently of `--gcmode`, `--history.state` and `--history.chain`, so an archive operator who wants fast log search back to genesis has to set `--history.logs 0`, which takes about 61 GB according to the v1.15.6 release notes. Status: by design.
- **Nethermind's `Receipt.MaxBlockDepth` is changing meaning** — on the 2.0.0 tag it defaults to 1,000, caps the width of an `eth_getLogs` range, and is ignored when the log index is on; on master it defaults to 10,000 and counts only the blocks read without the index. 1.39.2 had introduced the explicit limit at 10,000. A number quoted for one release is wrong for the next, which is why the lessons give none. Status: open, in flux.
- **Erigon's filtered `eth_getLogs` can miss old matches on non-archive nodes** — Erigon's docs say address- or topic-filtered queries older than the state-history window can miss matches even when every receipt is kept (`--prune.include-receipts --prune.receipts.distance=keep-all`), because the log indexes are retired with that window, while unfiltered queries still work. The answer is incomplete and carries no error. Status: by design (documented).
- **SSV works around dropped `eth_getLogs` results** — SSV's execution-client wrapper cross-checks every empty block in a log query against the header's logs bloom and retries it, attributing all-or-nothing drops to "a known Geth bug". The Geth issue itself was not found, so the claim is SSV's and unverified. Status: open, unverified.
- **No standard way to find the transaction that consumed a nonce** — Erigon and Reth serve `ots_getTransactionBySenderAndNonce` and Reth also `eth_getTransactionBySenderAndNonce` (Erigon has only the `ots_` form, erigon #23733), while Geth has neither. Detecting a replaced transaction elsewhere means inferring it from `eth_getTransactionCount`. Status: open, upstream.
- **Geth allows one in-flight transaction per EIP-7702 delegated account** — Geth's pool rejects a second pending transaction from a delegated sender (`in-flight transaction limit reached for delegated accounts`) and gapped nonces, replacements excepted. Senders that pipeline from delegated EOAs see rejections from Geth nodes; other clients' policy was not checked. Status: by design (pool policy).
- **Nethermind reports a zero-value block reward in every post-merge `trace_block`** — its trace module wraps the reward calculator in `MergeRpcRewardCalculator` on every chain, so each post-merge block gets one synthetic value-0 `block` reward entry: noise on mainnet, and on Gnosis a mask over a real payout, because the POSDAO reward contract still mints bridged xDAI by a system call after every block while the replayed trace shows only the zero entry. Pre-merge Gnosis blocks carry `external` reward entries that Blockscout's Nethermind integration reads, so dropping reward entries altogether, as the draft #13528 does, loses Gnosis history. Whether Erigon does the same on Gnosis was not checked, and an earlier finding that the TraceStore plugin records the real payouts was not re-checked. Status: open.
- **Nethermind's builder-submission validation is Deneb-shaped** — its Flashbots module declares only `flashbots_validateBuilderSubmissionV3`, whose request carries a V3 execution payload and a `BlobsBundleV1` and no execution requests, so it cannot validate the V4 (Electra) or V5 (Fulu) submissions mev-boost-relay sends on mainnet today. Checked on master, 2026-09-28. Status: open.
- **Nethermind 2.0.0 does not check a builder submission against its header by default** — `Flashbots.EnableValidation` defaults to `false` on the 2.0.0 tag, and with it off the block is executed with `ProcessingOptions.NoValidation`, so a submission whose state root, receipts root, gas used or logs bloom does not match execution is still reported valid. #13452 (merged 2026-09-23, after 2.0.0) makes `true` the default; switching it off still reports such a block valid, which the option's description now says. Status: open on 2.0.0, resolved on master.
- **Nethermind defaults CORS to `*` and has no Host allow-list** — `JsonRpc.CorsOrigins` defaults to `*` in 2.0.0 and on master, and the JsonRpc options have nothing like Geth's `--http.vhosts` or Besu's `--host-allowlist`. Any web page open on the same machine can therefore read a local node's JSON-RPC, and DNS rebinding is not stopped server-side; only browser protections such as Chrome 142's Local Network Access prompt stand in the way. Read from source, not tested from a browser. Status: open.
- **Nethermind's documentation lags 2.0** — the plugins guide and JSON-RPC sample still show `Init(INethermindApi)` and `InitRpcModules()`, removed in July 2026 (#12241, #12294, #12326) in favour of an Autofac `Module` with `IStep`s and `RegisterSingletonJsonRpcModule`. The database page still describes `state` as Patricia trie nodes and lists the LES `canonicalHashTrie`, and the state-pruning page does not say that copy-style full pruning is unavailable on the flat backend (2.0 known issue #13600). Status: open, upstream.
- **Relay data is self-reported and overlaps** — `proposer_payload_delivered` is each relay's own claim, builders submit the same block to many relays, and MEV-Boost sends the signed blinded block to every configured relay rather than only the one whose bid won. One slot can therefore appear as delivered at several relays. Status: by design.
- **A distributed validator in builder mode proposes only builder blocks** — Charon's `--builder-api` help says it "will only produce builder blocks", so a cluster that enables it gives up the local-payload fallback the builder spec expects an honest proposer to keep. Status: by design.
- **Clef no longer ships with Geth** — go-ethereum removed `cmd/clef` on 2026-06-03 (#35097, "no longer maintained"); v1.17.3 was the last release that shipped it, and the code continues at ethereum/clef. Geth keeps `--signer` and Nethermind still has a Clef signer plugin, but guides that install Clef alongside Geth are out of date. Status: by design.
- **Helios `eth_getLogs` proves inclusion, not completeness** — Helios verifies the receipts of the blocks that returned logs, but never checks blocks the provider left out, so a provider that omits logs is not caught. Status: by design.
- **Helios fee answers are constants** — `eth_maxPriorityFeePerGas` returns a hard-coded 1 gwei, and `eth_gasPrice` returns the verified base fee plus 1 gwei. Status: by design.
- **Besu leaves `safe` and `finalized` unset on BFT networks** — Besu reads both from markers that only the Engine API or a plugin sets, so `eth_getBlockByNumber("finalized")` on a plain QBFT or IBFT 2.0 network returns `-39001 Unknown block` although every block is final; the plugin API gained setters for PoA networks (Besu #7382). Libraries that default to `finalized` break there. Read from source. Status: open.
- **Besu account permissioning is not a consensus rule** — per Besu's local-permissioning docs, a node refuses non-allowlisted senders at submission and will not include them, but imports blocks from other nodes that do. Status: by design.
- **Geth's `earliest` quietly means the pruning cutoff** — `eth_getLogs` with `fromBlock: "earliest"` starts at the node's history cutoff without an error, while an explicit block number below the cutoff returns `4444`. A backfill that asks for everything since `earliest` gets a truncated answer that looks complete. Status: open.
- **A Geth archive keeps twelve days of state history unless told otherwise** — `--history.state` defaults to 90,000 blocks even with `--gcmode archive`, so a node configured as an archive answers historical state only about twelve days back until `--history.state 0` is set, and the history it did not keep cannot be recovered. The database-pruning docs page still describes path-based pruning as forthcoming. Status: by design; docs upstream.
- **`eth_createAccessList` returned `storageKeys: null` from one endpoint** — a load-balanced public endpoint reporting reth/v2.5.2 returned `null` where the spec requires an array; which backend produced it could not be established. Parsers that iterate the field crash on it. Status: open, unverified.
- **`eth_call` skips the EIP-7825 gas cap that `eth_estimateGas` applies** — Geth builds call messages with `SkipGasLimitCapCheck`, Nethermind enforces the 16,777,216 cap only in its transaction validator, and Reth behaves the same, yet all three clamp `eth_estimateGas` to it. On 2026-10-29 a loop of about 20,000,000 gas ran under `eth_call` on Geth 1.17.9 and Reth 2.8.0 while `eth_estimateGas` failed with `gas required exceeds allowance (16777216)` (Geth) and `-32003 out of gas: gas required exceeds: 16777216` (Reth), so a quote can succeed with more gas than any real transaction can carry since Fusaka. Status: open.
- **A simulated call can tell it is being simulated** — with no fee fields Geth runs `eth_call` with `tx.gasprice` 0 and lowers the block's base fee to 0, with no `from` the origin is the zero address (Nethermind too), and with no `gas` the call gets Geth's `--rpc.gascap` of 50,000,000, far above what any real transaction may carry, a gap Geth master keeps under Amsterdam (`SkipExecutionGasCapCheck`). A "red pill" contract, ZenGo's name for one that behaves when simulated and steals when run, keys on exactly these, so a wallet preview that omits fees, sender and a realistic gas limit can be gamed. Status: by design.
- **Deployless call results must pass the code-deposit rules** — an `eth_call` with no `to` returns the bytes its initcode passes to `RETURN`, and clients check them as new contract code: over 24,576 bytes fails (EIP-170), a leading `0xEF` fails (EIP-3541), and each byte costs 200 gas. Nothing in execution-apis says so and viem's deployless wrapper returns the raw data, so a deployless read of a `bytes32` that starts with `0xef` fails about once in 256 calls and a deployless multicall fails once its result passes 24 KB; reproduced on Geth 1.17.9 and Reth 2.8.0. Status: open (by design in the EVM, unhandled by tooling).
- **Clients word creation-result failures differently** — for a 24,577-byte deployless result Geth 1.17.9 returns `-32000` `max code size exceeded: code size 24577 limit 24576` and Reth 2.8.0 returns `-32003` `EVM error: CreateContractSizeLimit`; for a result starting with `0xEF`, Geth says `-32000` `invalid code: must not begin with 0xef` and Reth `-32003` `EVM error: CreateContractStartingWithEF`. Behind a balancer that mixes the two, neither the code nor the message can be matched. Status: open.
- **Pool rejection errors are unspecified, and Besu's differ** — Geth, Nethermind and Reth return `nonce too low`, `already known`, `replacement transaction underpriced` and `transaction underpriced` under `-32000`, while Besu returns `Known transaction` (`-32000`), `Nonce too low` (`-32001`), `Nonce too high` (`-32006`) and `Transaction nonce is too distant from current sender nonce`. Relayers keep per-client substring tables that go stale: OpenZeppelin Relayer lists `exceeds next nonce` as Nethermind's text, which now says `nonce too high` or `nonce too far in future`, and `nonce too far in the future` as Besu's. Status: open.
- **The full-transaction flag on `newPendingTransactions` has three shapes** — Geth, Erigon and Reth accept a bare `true` as the second parameter, Nethermind accepts `true` or `{"includeTransactions": true}`, and Besu only the object form (read from source). Geth's pubsub docs list no parameter at all and execution-apis does not specify `eth_subscribe` parameters, so a library cannot ask for full transaction objects portably. Status: open.
- **Geth's `newHeads` can skip heights** — Geth documents that when several blocks are imported at once only the last is emitted, so a gap in block numbers does not prove a dropped connection. Status: by design.
- **Geth's docs and code disagree on what drops a slow subscriber** — the pubsub page (Considerations, item 4) says notifications are kept in an internal buffer and the connection is closed once it holds "currently 10k", but go-ethereum master keeps no such buffer: `Notifier.send` in `rpc/subscription.go` writes each notification directly with `context.Background()`, so `writeJSON` in `rpc/json.go` applies `defaultWriteTimeout`, 10 seconds, and once a consumer stops reading long enough for one write to stall that long, the write times out and the connection, WebSocket or IPC, breaks. Either way every subscription on the connection is lost. Separately, Geth's own Go client drops a subscription with `ErrSubscriptionQueueOverflow` once 20,000 notifications wait unread on its side (`maxClientSubscriptionBuffer` in `rpc/client.go`). Status: open, upstream (docs out of date).
- **The beacon `block` and `head` events come in a client-dependent order** — beacon-APIs does not fix it; Lighthouse since v8.1.0 emits `head` before `block` (`import_block` in `beacon_chain.rs` registers the head event before `import_block_update_metrics_and_events` registers the block event), Prysm's order could not be confirmed, and Teku, Nimbus, Lodestar and Grandine were not checked. A consumer that times "import" from `block` measures a different instant on different clients. Status: by design.
- **`trace_filter` behaves differently on every client that has it** — Geth has none; Erigon looks addresses up in its call-trace indexes and re-executes the matching transactions, while Nethermind, Besu and Reth replay every block in the range. Erigon (`--rpc.blockrange.limit`, since v3.4.0) and Besu (`--rpc-max-trace-filter-range`) reject ranges over 1,000 blocks by default, Reth (`--rpc.max-trace-filter-blocks`) over 100, and Nethermind has no cap and runs until its request timeout, so a wide address-history query fails at a different width on each and no method reports the limit in advance. Status: open.
- **A load-balanced endpoint is several nodes, and not always one client** — TRM's engineering blog compares block hashes across `eth_getBlockByNumber`, `eth_getBlockReceipts` and `trace_block` for every block and retries the batch on disagreement, because a provider's balancer routes the calls to nodes on different branches. On 2026-10-29 `ethereum-rpc.publicnode.com` answered `web3_clientVersion` with `reth/v2.8.0` on one call and `Geth/v1.17.9` on the next, so error codes, version strings and capability answers can change between two calls. Status: by design.
- **Some endpoints cannot serve state by block hash** — since Foundry v1.8.0 every fork read names the fork block by hash as an EIP-1898 object (foundry-core #157), so a chain whose RPC rejects state by hash fails every read: foundry #16774 names Somnia mainnet ("-1 unable to load historical state"), and Rootstock and Moonbeam forced two changes to the wire form within 1.8.x. Foundry added `--fork-state-by-number` to Anvil (#16774) and to `forge test` and `forge script` (#17352, where number-based reads skip the disk cache), which means the only reorg-safe way to pin state is not portable across endpoints. Status: open.
- **Foundry probes the Reth-only `eth_getAccountInfo`** — its fork backend races `eth_getAccountInfo` against `eth_getBalance`, `eth_getTransactionCount` and `eth_getCode` for the first account and keeps whichever path answers, so every fork start against Geth logs a `-32601`, and behind a balancer that mixes Reth with other clients the path flips between requests. The method is in Reth but not in execution-apis. Status: by design.
- **`eth_capabilities` means different things on different clients** — Geth's `logs.oldestBlock` is its log-index tail although `eth_getLogs` below it still answers through an unindexed scan, and Geth computes every floor from configuration, so a path-based archive still building its state index reports history it cannot serve yet. Besu reports one `oldestBlock` for all resources and no `deleteStrategy`, and since 26.6.0 marks `state` and `stateproofs` disabled whenever genesis state is missing, as on every snap-synced Bonsai node; Nethermind returns `tx` and `logs` as copies of `receipts`, and Erigon disables `stateproofs` without `--prune.include-commitment-history`. Status: open.
- **Early `eth_capabilities` releases wrote `retentionBlocks` as a JSON integer** — the merged schema says hex QUANTITY, but Reth v2.3.0 (fixed in v2.4.0) and Nethermind 1.39.0 to 1.39.3 (fixed in 2.0.0) emit a plain number. A router has to accept both encodings until deployed nodes catch up. Status: resolved upstream; deployed nodes lag.
- **Nethermind rejected a near-head `safeBlockHash` before 1.38.0** — it validated `safeBlockHash` against its current canonical chain rather than the new head in the same request, so valid forkchoice updates driven by the Fast Confirmation Rule got `-38002 Inconsistent ForkChoiceState - safe block hash` (nethermind #11185, fixed by #11187 in 1.38.0). Nimbus stopped sending the rule's result as the safe hash in v26.5.0 (#8280) and resumed in v26.6.0 (#8538); whether other execution clients accept a safe hash near the head, or one that moves backwards, was not checked. Status: resolved in Nethermind; others unverified.
- **Geth still converts old blob wrappers on submission** — `eth_sendRawTransaction` and `eth_sendRawTransactionSync` turn a version-0 sidecar (one proof per blob) into version 1 by computing cell proofs (`sc.ToV1()`), under a "TODO: remove in go-ethereum v1.17.x" still on master after v1.17.10. Wallets that still send version 0 work against Geth and will fail when the conversion goes, and possibly already against other clients, which were not checked. Status: open.
- **Hive's documentation and published listing are out of step with hive** — `docs/overview.md` still describes an `ethereum/rpc` simulator that no longer exists (the directory now holds `consensus`, `eels`, `engine`, `graphql`, `rpc-compat` and `sync`), and the README promises two public instances and lists one. In `hive.ethpandaops.io`'s `listing.jsonl` the `nimbus-el_default` version is a multi-line string that runs on into `--help` output, which breaks tools that parse versions from it. Status: open, upstream.
- **mev-boost-relay documents a 3,000 ms simulation timeout but uses 10,000 ms** — the README gives `BLOCKSIM_TIMEOUT_MS` a default of `3000`, while `services/api/blocksim_ratelimiter.go` on `main` reads `cli.GetEnvInt("BLOCKSIM_TIMEOUT_MS", 10000)`. An operator who trusts the README budgets for a deadline a third as long as the one the relay enforces. Status: open, upstream (docs).
- **Teku's docs give two paths for slashing-protection data** — the `slashing-protection` reference says export reads "the `slashprotection` directory under the validator client data directory", which defaults to `<data-path>/validator`, while its import section names `<data-path>/validators/slashprotection/`. A migration between machines is exactly when a wrong path means signing without history. Status: open, upstream (docs).
- **Lighthouse doppelganger protection needs a Lighthouse beacon node** — the Lighthouse Book says the feature "is not yet interoperable", so a Lighthouse validator client with it enabled must run against a Lighthouse beacon node. Status: by design.

### Layer 2 differences

The rollups present an Ethereum-shaped API over quite different machinery, and the differences are where the bugs are.

- **Node topology differs** — an OP Stack node is `op-node` plus a separate execution client, while Arbitrum Nitro is a single process. Operational assumptions do not carry across.
- **L1 cost is surfaced under three different names** — OP Stack puts `l1Fee`, `l1GasUsed` and `l1BaseFeeScalar` on the receipt, Arbitrum reports `gasUsedForL1` alongside `l1BlockNumber`, and zkSync uses `l1BatchNumber` and `l1BatchTxIndex`. Nothing is shared.
- **`eth_estimateGas` means different things** — it excludes the L1 data fee on OP Stack and includes it on Arbitrum, so the same call returns figures that are not comparable.
- **`block.number` inside the EVM is not the same number** — on Arbitrum it approximates the L1 block number ("close to (but not necessarily exactly)", per Arbitrum's docs), and on OP Stack it is the L2 block number. Contract logic that reads it behaves differently per chain: an OpenZeppelin block-number vote clock on Arbitrum reports `mode=blocknumber&from=default` while its checkpoints are keyed by those L1-like numbers, so a reader that passes Arbitrum's own block number reads the wrong checkpoint, and ERC-6372's `from=<CAIP-2 id>`, meant for this case, goes unused. Status: by design.
- **`PREVRANDAO` is not randomness on some L2s** — on Arbitrum `block.prevrandao` returns the constant 1, so contracts ported unchanged silently lose their entropy. Status: by design.
- **`P256VERIFY` at `0x100` differs per chain** — L1 (EIP-7951, Fusaka) charges 6,900 gas and fixes two RIP-7212 flaws, a missing point-at-infinity check and a wrong modular comparison; rollups that follow RIP-7212 charge 3,450; and on a chain with neither, a call to `0x100` succeeds with empty output, which reads as an invalid signature. Gas budgets and correctness assumptions do not port even though the address and interface match. Whether OP Stack chains later moved to EIP-7951's price or fixes was not checked. Status: open.
- **An ordinary beacon node may not serve blobs** — under PeerDAS a node custodies at least 4 of 128 column groups, so without `--supernode` or `--semi-supernode` (Lighthouse, Prysm; `--supernode` or `--semiSupernode` on Lodestar) it may not answer the blobs route at all, even inside the retention window. Rollup nodes (`--l1.beacon`), op-challenger (`--l1-beacon`) and Nitro (`--parent-chain.blob-client.beacon-url`) all need such an endpoint. Status: by design.
- **The reference blob archiver does not validate its source** — `base/blob-archiver`'s README says neither the archiver nor its API validates what the beacon node returned (its issue #4), so consumers must recompute the KZG commitments themselves, as op-node does. Status: open, upstream.
- **op-node's `--l1.rpckind=nethermind` avoids `eth_getBlockReceipts`** — op-node maps `nethermind` to `parity_getBlockReceipts`, with batched per-transaction receipt calls as the fallback, while `standard` uses `eth_getBlockReceipts`. `Parity` is in Nethermind 2.0's default module list, but on a Nethermind L1 whose `JsonRpc.EnabledModules` leaves it out, op-node fetches every receipt separately. Status: open.
- **op-node's `optimism_` namespace mixes number encodings** — `optimism_safeHeadAtL1Block` takes a hex quantity, but `optimism_syncStatus` and the safe-head response return block numbers as plain decimal JSON numbers. Status: by design.
- **Fault-proof hosts depend on non-standard RPC** — kona-host, behind op-challenger's default `cannon-kona` game type, reads L1 data with `debug_getRawHeader` and `debug_getRawReceipts` (both in execution-apis), but L2 witnesses with op-reth's `debug_executePayload`, falls back to `debug_dbGet`, a raw database read whose key layout is client-specific, and needs historical `eth_getProof` from op-reth's proofs-history store. The op-challenger docs now require an op-reth archive node specifically. Status: open.
- **The rollup node's safe-head database is irreproducible local history** — `optimism_safeHeadAtL1Block` works only if `--safedb.path` was set, returns not-found for L1 blocks from before it was enabled, and per the op-challenger docs must never be restored from a snapshot, yet op-challenger's honest-block bound depends on it. Status: by design.
- **OP Stack predeploy methods depend on block height** — predeploys are proxies upgraded by network-upgrade transactions, so `GasPriceOracle.getL1FeeUpperBound` (Fjord) reverts at older blocks, and `getL1GasUsed`, deprecated since Fjord, "will revert … in a future upgrade". Historical fee re-estimation has to choose the method per block. Status: by design.
- **Alt-DA's availability challenge covers keccak commitments only** — the spec implements resolving input data through the `DataAvailabilityChallenge` contract only for `type=0` (keccak) commitments, so chains using DA-service commitments have no on-chain availability challenge at all. Status: by design.
- **Helios's OP Stack mode trusts the sequencer key** — it accepts unsafe blocks signed by the chain's unsafe-block signer, whose address it can optionally check against the L1 `SystemConfig`, rather than L1-settled outputs. Status: by design.
- **Arbitrum `arb_` method names could not be confirmed** — the lesson points at the NodeInterface precompile instead. Status: open, needs someone who runs a Nitro node.
- **Library defaults are unspecified** — viem, ethers, web3.py and alloy each pick their own default block tag, retry policy, gas multiplier and revert-data handling, and none of it is part of any spec. Two libraries against one node can disagree. Status: open.
- **Oracle prices freeze with the sequencer, and the down flag arrives late** — Chainlink's L2 sequencer uptime flag is sent from L1 (OP Stack through `L1CrossDomainMessenger`, Arbitrum through the delayed inbox), so it lands only when the sequencer resumes, ordered before transactions queued after it, and consumers need a grace period on top (3,600 s in Chainlink's sample). Chainlink is no longer expanding these feeds to new networks, so newer L2s may have none. Status: by design.
- **OP Stack fee recomputation depends on the fork** — Isthmus added an operator fee, `operatorFeeConstant + gasUsed × operatorFeeScalar ÷ 10^6` with both parameters read from `L1Block` at `0x4200…0015`, Jovian changes the scalar term to "× 100" per the OP docs, and the base fee goes to `BaseFeeVault` rather than being burned. A reconciliation that recomputes a sender's fee has to apply each block's fork rules. Status: by design.
- **A contract address on one chain says nothing about the same address on another** — a key controls its address on every EVM chain, but a contract exists only where it was deployed, and whoever reproduces the deployment elsewhere takes the address there. In 2022 an attacker took 20 million OP that the Optimism Foundation had sent to Wintermute's L1 Safe address on Optimism by deploying a Safe there first, and exchanges that hand out CREATE2 forwarder addresses face the same problem with deposits sent on the wrong chain. Status: by design.
- **Hyperlane signs Ethereum messages long before finality** — the Hyperlane registry sets `reorgPeriod` to 15 blocks for Ethereum (about three minutes), 10 for Base, 5 for Arbitrum and `finalized` only for Polygon, and validators sign a message's checkpoint once it is that deep, well before Ethereum's roughly 13-minute finality. Safety past that depth rests on slashing validators who sign reorged messages, so a deep Ethereum reorg would be a cross-chain double spend. Status: by design.
- **Across's documentation disagrees with its contracts and with itself** — the intent-lifecycle page describes `depositV3`, `V3FundsDeposited`, `fillV3Relay` and `FilledV3Relay`, while the current `V3SpokePoolInterface.sol` emits `FundsDeposited` and `FilledRelay` from `deposit` and `fillRelay` and keeps the V3 events only as legacy definitions, so an indexer written from the docs filters on topics new deposits no longer emit. The actors page also puts relayer capital lock-up at "~1.5 hours" where the speed page says "2 hours worth of liveness". Status: open, upstream.

## Gaps in this map

Terms a lesson had to explain in prose because no node exists for them. Each is a candidate node; the slug is the proposed id.

The eleven terms listed here until 2026-10-29 all have lessons now and are under **Resolved**. The terms below were met while writing those lessons.

- `glamsterdam` — the upgrade after Fusaka: Gloas, with enshrined proposer-builder separation, on the consensus side, and Amsterdam, with block-level access lists, EIP-7708 transfer logs, EIP-8282 builder requests and EIP-8037's change to the gas cap, on the execution side. Eleven lessons explain it in a clause, and several repeat its status (live on Sepolia since 2026-10-06, Hoodi's activation withdrawn, no mainnet date), which one node could hold.
- `block-access-list` — EIP-7928, the per-block record of every account and storage slot a block touches, committed in the header as `blockAccessListHash`. The system-contracts lesson explains it in a clause, and no lesson says how a caller reads one.
- `eip-7708` — the Amsterdam change that makes every ether transfer emit a `Transfer` log from `0xffff…fffe`, which the transaction-simulation lesson explains because it changes what `traceTransfers` does and what indexers can see.
- `permit2` — Uniswap's signature-approval contract, which the eip-3009 and x402 lessons explain as the payment path for tokens without EIP-3009 and the transaction-simulation lesson as a drainer's signing target.
- `fee-on-transfer-token` — tokens that keep a cut of each transfer, which the token-standards and dex-aggregator lessons each describe in a clause, with nowhere to say how their logs and balances differ.
- `stealth-address` — ERC-5564 stealth addresses and their announcer contract, explained inside the rpc-privacy lesson.

## Facts we would not assert

Deliberately left vague in the lessons because they could not be confirmed. Anyone who knows the answer should fix the lesson and move the entry to **Resolved**.

- The terminal total difficulty value that triggered the Merge.
- Slashing penalty constants after Electra changed the minimum-penalty quotient.
- The weak subjectivity period as a number, rather than "weeks, read what your client computes".
- Which `eth_` methods the Portal Network actually serves today.
- Blob targets after the blob-parameter-only forks; the lessons give only the maxima. Geth's default BPO configs say 10 and then 14, which were not checked against any network's config.
- The current mainnet block gas limit, which validators keep voting upward. It was 60,000,000 at slot 15307259 on 2026-09-27 according to ethPandaOps' Lab, but any number goes stale.
- Default ports for Nethermind and Besu metrics endpoints.
- Arbitrum's challenge period, written as comparable to OP Stack's seven days rather than given.
- OP Mainnet's dispute-game clock (`MAX_CLOCK_DURATION`) and `DelayedWETH` delay as numbers, written as "a withdrawal delay".
- The status of web3.js, written as "no longer the recommended starting point" rather than sunset.
- Canonical ERC-4337 EntryPoint addresses; the lesson points at `eth_supportedEntryPoints` instead.
- Whether every wallet requires EIP-712 typed data as a JSON string, written as "most".
- How much of the `eth_` surface verified-RPC proxies other than Helios cover, written as partial and moving between releases. Helios itself is now described from source: `eth_call`, `eth_estimateGas` and `eth_createAccessList` re-executed against proven state, `eth_getLogs` proven for inclusion only, and fee methods answered with constants.
- Flags for keeping historical beacon states on Prysm and Lodestar, and whether Lighthouse still accepts `--reconstruct-historic-states`; only Lighthouse `--archive`, Teku `--data-storage-mode=archive` and Nimbus `--history=archive` were verified.

- OP Stack's `PREVRANDAO` value, believed to be the L1 origin's mix.
- What `eth_getTransactionReceipt` returns for a Base Flashblocks preconfirmed transaction; Base's docs and providers' docs disagree.
- Whether Geth caps the block range of `eth_getLogs`. Its docs show no cap, and `--rpc.logquerylimit` (v1.16.4) caps addresses per filter, not blocks.
- What Reth returns from `eth_getBlockReceipts` for a block whose receipts were partly pruned by `--prune.receiptslogfilter`.
- Queued-transaction lifetimes and restart journaling on clients other than Geth, whose `--txpool.lifetime` 3h and `--txpool.journal` are the only ones cited, and replacement bumps on Erigon and Besu.
- Whether Nethermind, Erigon, Besu or Reth stop an in-flight `eth_call` when the HTTP client disconnects; Nethermind is said only to bound it by `JsonRpc.Timeout`.
- Default `debug_trace*` timeouts on clients other than Geth, whose default is 5 seconds.
- Which validator clients work with Web3Signer, and with which flags, written as "the major validator clients".
- Whether Teku sends its Fast Confirmation Rule result as `safeBlockHash` when `--Xfast-confirmation-enabled` is on; its rollout issue #10994 implies so, but the code was not read.
- When execution clients other than Geth move `latest` and emit `newHeads` (Geth does so on `engine_forkchoiceUpdated`, not on `engine_newPayload`), and whether they serve state by hash for a block that `engine_newPayload` executed but fork choice has not yet made canonical.
- Which clients apply `authorizationList` inside `eth_call`, which ERC-8010 signature verification needs; only the execution-apis schema and Geth's `TransactionArgs` were checked.
- Client flags and thresholds for late-block reorgs by the next proposer, written as "can be reorged out by the next proposer".
- How each L2 stack derives `finalized`, written as waiting for the batch to settle on Ethereum.
- Exchanges' confirmation counts for ether deposits; no official figure was found, so the lessons use Circle Mint's and Allium's published tables instead.

- **Validator custody after Fulu** (was a fact we would not assert) — a node custodies 4 custody groups without validators and, with validators attached, one group per 32 ETH of their effective balance, at least 8 and at most 128 (`VALIDATOR_CUSTODY_REQUIREMENT`, `BALANCE_PER_ADDITIONAL_CUSTODY_GROUP`, `specs/fulu/validator.md`), so 4,096 ETH or more makes it a supernode. The peerdas lesson states it.
- **Blob maxima after the blob-parameter-only forks** (was a fact we would not assert) — 15 from epoch 412672 (2025-12-09) and 21 from epoch 419072 (2026-01-07), per eth-clients/mainnet `config.yaml`; the peerdas lesson states the current 21. The targets remain under Facts we would not assert.
- **Replacement bumps on Nethermind and Reth** (part of a fact we would not assert) — both demand at least 10 percent more on both fee fields, like Geth (Reth's `--txpool.pricebump`, default 10; Nethermind's `CompareReplacedTxByFee`, fixed at 10 percent), and Geth's blob pool demands 100 percent; the transaction-relayer and transaction-lifecycle lessons state them. Lifetimes, journaling, Erigon and Besu remain open.

- **The Nethermind lesson predated Nethermind 2.0** — rewritten against the 2.0.0 release notes, source and docs: the flat state backend is the default for new databases while an upgraded patricia database stays patricia, flat history comes in four shapes and fails closed below its floor, historical proofs are opt-in, copy-style full pruning works on patricia only, and the mainnet ancient barriers moved to 24,600,000. The storage-engine lesson was updated to match.
- **About forty passages in older lessons were wrong or out of date** — verifying facts for the sixty-two new topics turned them up. The largest: the execution-apis docs URL cited 45 times and every consensus-specs `dev`-branch link were dead; three examples read USDC's proxy implementation slot as a balance and one override wrote a 33-byte value; the attestation example had the pre-Electra shape; six lessons named the deprecated `blob_sidecars` route; `ots_` was called Erigon-only; Besu was still credited with Clique and Tessera privacy, and Geth with Clef; the account-proof lesson gave one client family's absent-account fields as universal, and one of its checkpoint questions had a wrong answer; sync-committee thresholds were overstated; PREVRANDAO was called usable randomness; the execution-apis lesson missed `debug_trace*`, `txpool_` and `eth_capabilities`; L2 deposits were said to always alias the sender; the EIP-7825 gas cap, the `4444` pruned-history error, and Helios's general `eth_call` verification were missing. Twenty-nine aliases that pointed search at older lessons now belong to the new topics.

- **`ots_` is only confirmed on Erigon** — checked across clients: Reth implements all but the two address searches, Anvil all of it, and Geth, Nethermind and Besu none. Recorded as "`ots_` support is uneven" under Client behaviour.
- **Transaction-index retention is a Geth-documented number only** — Nethermind's `Receipt.TxLookupLimit` has the same 2,350,000-block default, and Reth keeps its `transaction_lookup` segment under `--full` and prunes it under `--minimal`; folded into the transaction-index entry, where Erigon and Besu are still unchecked.
- **`EIP-7623` calldata cost and what `requestsHash` hashes** (were facts we would not assert) — a non-creation transaction pays `21000 + max(4 × tokens + execution gas, 10 × tokens)`, tokens being zero bytes plus four times non-zero bytes, with refunds subtracted before the comparison; `requestsHash` is the SHA-256 of the concatenated SHA-256 of each non-empty `type ++ data`, in ascending type order, so `sha256("")` when there are none. The gas-refunds and execution-requests lessons state both.
- **Whether `blob_sidecars` remains the Beacon API blob route** — it does not: beacon-APIs v4.0.0 deprecated it for `/eth/v1/beacon/blobs/{block_id}` (#546) and the v5 alphas remove it; see "The Beacon API blob route moved".
- **The OP Stack sequencing window as a number** — the standard value is 3,600 L1 blocks, 12 hours, per the OP Stack rollup deployment configuration reference.
- **Whether Nethermind's default `JsonRpc.EnabledModules` includes `Trace`** — it does: the 2.0.0 default is `[Eth,Subscribe,Trace,TxPool,Web3,Proof,Net,Parity,Health,Rpc]`, confirmed in source.
- **Whether `--rpc.batch-request-limit` and `--JsonRpc.JwtSecretFile` are real flag names** — both are: Geth's `--rpc.batch-request-limit` defaults to 1,000 (with `--rpc.batch-response-max-size` at 25,000,000), and `JsonRpc.JwtSecretFile` is a Nethermind 2.0.0 key.
- **Helios command-line flags** — verified from its README: `--execution-rpc`, `--consensus-rpc`, `--checkpoint`, `--strict-checkpoint-age`, `--load-external-fallback`, `--rpc-port`, `--rpc-bind-ip`, `--data-dir` and `--network`.

- **About fifty lesson passages were wrong or out of date** — reviewing every checkpoint against its lesson turned them up across all eleven lesson files, two of them from the example text the original writers were given. Among them: a hex example decoded to the wrong number, `safe` described as trailing the head by under one epoch, `contractAddress` said to be null on a reverted deployment, Teku and Lodestar given Lighthouse's Beacon API port, a proposer said to validate a builder's payload before signing it, aggregates said to travel on the attestation subnets, Geth's path-based storage dated to v1.13 instead of v1.14, the blob fee said to fall to 1 wei after Fusaka, and a storage key one hex digit too long. All are corrected, and no checkpoint question tests any of the old claims.

- **Checkpoints were partly machine-written and gave answers away by length** — two of every five questions were generated fill-in-the-blanks that offered topic titles for a gap in a sentence, so the right option often did not fit and a wrong one sometimes did; and across the 558 hand-written questions the correct option was the longest 79% of the time, where chance is 25%. The generator is deleted, every topic has six reviewed hand-written questions of at least four kinds, and tests hold the correct option to no more than 1.2 times the longest wrong one and to being the longest in at most 35% of questions.

- **`rpc` linked to itself** — the lesson contained `[[rpc|RPC]]` inside its own body, rendering a button that reloaded the page you were on. Removed from the dataset, and the renderer now prints a self-link as plain text. A test forbids it.
- **`validator-node` id drift** — content referenced an id that the registry had renamed to `validator-client`, producing dangling links. All references updated; the validator now rejects unknown ids.
- **A generated question printed its own answer** — when a lesson linked the same term twice in one sentence, the fill-in-the-blank question blanked the first mention and left the second visible. The generator now blanks every mention, and a final filter drops any question whose prompt contains its answer.
- **Edges snapped while nodes glided** — CSS cannot transition SVG line geometry, so map transitions were half-animated. Nodes and edges are now driven by one frame loop.
- **Lessons were too short to teach** — the original dataset averaged about sixty words per topic. The rewrite runs 280 to 600 words with worked examples and pitfalls, and the tests enforce a floor.
